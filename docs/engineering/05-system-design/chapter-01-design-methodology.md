# 系统设计方法论

## 1. 设计流程

```
需求分析 → 概要设计 → 详细设计 → 评审 → 实现
```

## 2. 需求分析

- 功能需求：系统做什么
- 非功能需求：性能、可用性、扩展性

## 3. 概要设计

- 系统架构图
- 模块划分
- 接口定义
- 数据流图

## 4. 详细设计

- 类图
- 时序图
- 状态图
- ER图

## 5. 设计文档模板

```markdown
# 系统设计文档

## 1. 概述
## 2. 需求分析
## 3. 架构设计
## 4. 模块设计
## 5. 接口设计
## 6. 数据设计
## 7. 非功能需求
## 8. 风险与对策
```

## 6. 需求分析的实践方法

### 6.1 功能需求分析

```java
/**
 * 需求分析的核心问题（5W1H）：
 * - What：系统要做什么？
 * - Who：谁在使用？
 * - When：什么时候用？
 * - Where：在哪里部署？
 * - Why：为什么需要这个功能？
 * - How：如何实现？
 */

// 示例：设计一个秒杀系统
// What：用户在指定时间抢购限量商品
// Who：普通用户、运营人员
// When：每天 10:00 开始，持续 1 小时
// Where：Web + App，部署在多个数据中心
// Why：促销活动，提升日活
// How：预热缓存 + 限流 + 异步下单
```

### 6.2 非功能需求分析

| 需求类型 | 关键指标 | 设计考量 |
|---------|---------|----------|
| 性能 | 响应时间 < 200ms，QPS > 10000 | 缓存、异步、数据库优化 |
| 可用性 | SLA 99.99%（年停机 < 52 分钟） | 冗余、故障转移、多活 |
| 扩展性 | 支持 10 倍流量增长 | 水平扩展、分库分表 |
| 安全性 | 防 DDoS、SQL 注入、XSS | WAF、输入校验、加密 |
| 可维护性 | 新功能开发周期 < 2 周 | 模块化、自动化测试 |

## 7. 设计评审 Checklist

```markdown
## 设计评审检查清单

### 架构层面
□ 是否有清晰的系统架构图？
□ 模块划分是否合理（高内聚低耦合）？
□ 是否识别了关键的技术风险？
□ 是否考虑了扩展性需求？

### 接口层面
□ API 设计是否 RESTful？
□ 接口是否有版本管理？
□ 错误处理是否完善？
□ 是否有接口文档（Swagger）？

### 数据层面
□ ER 图是否完整？
□ 索引设计是否合理？
□ 是否考虑了数据量增长？
□ 是否有数据备份和恢复方案？

### 非功能层面
□ 性能瓶颈在哪里？
□ 单点故障有哪些？
□ 安全风险有哪些？
□ 监控和告警方案是什么？
```

## 8. 常见设计陷阱

| 陷阱 | 表现 | 正确做法 |
|------|------|----------|
| 过度设计 | 为不存在的需求设计复杂方案 | 遵循 YAGNI，解决当前问题 |
| 忽视非功能需求 | 只考虑功能，忽略性能/可用性 | 早期明确非功能需求 |
| 技术选型跟风 | 看到新技术就想用 | 以解决问题为导向选型 |
| 缺少文档 | 设计决策没有记录 | 使用 ADR 记录关键决策 |
| 单人设计 | 一个人闭门造车 | 团队评审，集体智慧 |

> **设计的本质**：设计不是画漂亮的架构图，而是在约束条件下做出合理的权衡。好的设计是在“现在做对”和“未来能改”之间找到平衡点。
