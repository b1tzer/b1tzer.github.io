# B+ 树索引

## 1. 聚簇索引

- 主键索引，叶子节点存储完整行数据
- 一个表只能有一个聚簇索引
- InnoDB 默认使用主键作为聚簇索引

## 2. 二级索引

- 非主键索引，叶子节点存储主键值
- 查询需要回表（通过主键到聚簇索引查完整数据）

## 3. B+ 树结构

```
        [10 | 20 | 30]           ← 非叶子节点（只存键值）
       /    |    |    \
   [1-9] [11-19] [21-29] [31-40] ← 叶子节点（存数据或主键）
     ←─────────────────────→     ← 双向链表
```

## 4. 回表

```sql
-- 二级索引查询
SELECT * FROM users WHERE name = '张三';
-- 1. 在 idx_name 二级索引找到 name='张三' 的主键 id=5
-- 2. 回表：用 id=5 到聚簇索引查完整行数据
```

## 5. 索引下推 (ICP)

```sql
-- MySQL 5.6+ 支持
SELECT * FROM users WHERE name LIKE '张%' AND age = 25;
-- 在索引层直接过滤 age，减少回表次数
```

## 6. B+ 树高度与数据量关系

```
假设：主键 BIGINT (8字节) + 指针 (6字节) = 14字节
非叶子节点每页可存：16384 / 14 ≈ 1170 个键值
叶子节点每行假设 200 字节：16384 / 200 ≈ 80 行数据

高度=2：1170 × 80 ≈ 9万行
高度=3：1170 × 1170 × 80 ≈ 1亿行
高度=4：1170 × 1170 × 1170 × 80 ≈ 1000亿行
```

**结论：** 通常 B+ 树高度为 3-4 层，即可存储上亿数据。每次查询只需 3-4 次磁盘 IO。

## 7. 聚簇索引 vs 二级索引对比

| 特性 | 聚簇索引 | 二级索引 |
|------|---------|----------|
| 叶子节点内容 | 完整行数据 | 主键值 |
| 数量 | 一个表只有一个 | 可以有多个 |
| 查询速度 | 直接获取数据 | 需要回表 |
| 排序 | 天然有序 | 无序（需要排序） |
| 覆盖索引 | 天然覆盖 | 需要包含所有查询列 |

## 8. 自增主键 vs UUID 主键

```sql
-- ✅ 推荐：自增主键
CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    ...
) ENGINE=InnoDB;

-- ❌ 避免：UUID 主键
CREATE TABLE orders (
    id CHAR(36) PRIMARY KEY,  -- UUID
    ...
) ENGINE=InnoDB;
```

| 特性 | 自增主键 | UUID 主键 |
|------|---------|----------|
| 写入性能 | 顺序写，页分裂少 | 随机写，页分裂频繁 |
| 索引大小 | 8字节 | 36字节 |
| 二级索引大小 | 索引值小 | 索引值大（存主键） |
| 全局唯一 | 单库唯一 | 全局唯一 |
| 适用场景 | 单库单表 | 分布式环境 |

## 9. 索引的代价

**空间代价：**
- 每个索引都是一棵 B+ 树
- 索引越多，磁盘空间占用越大

**时间代价：**
- INSERT：需要维护所有索引
- UPDATE：如果修改了索引列，需要删除旧索引、插入新索引
- DELETE：需要删除所有索引中的记录

```sql
-- 查看表的索引大小
SELECT
    index_name,
    ROUND(stat_value * @@innodb_page_size / 1024 / 1024, 2) AS index_mb
FROM mysql.innodb_index_stats
WHERE table_name = 'users' AND stat_name = 'size';
```

## 10. 最佳实践

1. **主键选择 BIGINT AUTO_INCREMENT** — 顺序写入，空间效率高
2. **避免过多索引** — 一般不超过 5-6 个
3. **定期清理无用索引** — 使用 `sys.schema_unused_indexes` 检查
4. **理解回表成本** — 尽量使用覆盖索引
5. **避免在频繁更新的列上建索引** — 维护成本高
